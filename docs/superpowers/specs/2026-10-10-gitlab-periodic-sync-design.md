# GitLab Webhook 与定时同步

状态：用户已批准（2026-10-10）。首次同步只记录现有 MR 的提交基线；自动处理开启之后的新 MR 和新提交。

## 目标与范围

保留 GitLab Webhook 的实时通知，增加由服务器主动发起的定时同步。在 GitLab 不能访问回调地址时，智审台仍能自动发现、评审已接入仓库的变更，并按现有门禁检查自动合并。

每个项目独立启用同步，默认关闭，默认间隔 60 秒，可设置为 30–3600 秒。管理员可以请求立即同步，成员可以查看同步状态。混沌工程和应急管理在部署验证后启用同步。

## 架构

容器中增加由 Supervisor 管理的轻量同步进程，调用 Django 管理命令 `sync_gitlab_mrs --watch`。它与评审 worker 独立，AI 请求不会阻塞同步周期。继续使用现有数据库、单机文件锁和持久任务队列，不增加 Redis/Celery。

新增 `ProjectGitLabSync` 保存项目的开关、间隔、激活时间、下次执行时间、最近同步结果和失败次数；新增 `GitLabSyncBaseline` 保存每个项目仓库在激活时的 MR IID → SHA 基线。两者均随数据库持久化。

新增共享自动入队函数，供定时同步和 MR Webhook 调用。评论中的 `/review`、`/improve` 以及界面的手动评审保留明确重新评审的语义。

## 激活与首次同步

开启时，在项目同步锁内分页读取所有已启用仓库的 opened MR，记录其 SHA（包括草稿），读取完整且成功后才保存开关和基线。缺少 SHA、重复分页、超出读取预算或连接失败时拒绝激活，避免把未知旧 MR 当作新 MR。

基线 SHA 的 MR 不由自动同步触发评审。之后创建的新 MR，或基线 MR 的新 SHA，可以自动入队。再次关闭后开启会重新记录基线。新仓库首次纳入同步时也先记录基线。

## 同步与去重

每轮分页读取所有 opened MR；忽略草稿、停用仓库和暂停项目。使用项目、仓库路径、MR IID、SHA、完整评审类型组成自动事件身份。相同提交只创建一次自动任务，已经成功完成的手动完整评审也可以覆盖该提交。

在现有 MR 锁内完成检查和入队，避免 Webhook 和同步器并发创建重复任务。若该 MR 已有任务运行，下一轮同步继续检查最新 SHA，不丢失新提交。自动任务执行前核对预期 SHA；提交已变化时结束旧任务，等待最新提交入队。

真实 Webhook 的自动评审先通过 GitLab 获取当前 MR 状态和提交。以 MR 当前 SHA 定义自动任务；差异引用落后时使用现有退避重试等待，不使用旧差异进行分析。回调密钥校验保持在外部读取之前。草稿、关闭、已合并或基线提交返回忽略结果，API 故障返回可重试错误。定时同步不会模拟评论命令。

## 配置与界面

`GET/PATCH /api/projects/{id}/sync/` 读取和修改同步设置；仅允许写入 `enabled`、`interval_seconds`。`POST /api/projects/{id}/sync/run/` 请求后台立即执行，不在 HTTP 请求中运行 AI 或合并。

在项目评审策略页面增加独立同步卡片，提供开关、间隔、保存、立即同步、最近同步、下次同步、结果和错误。同步卡片独立保存，失败时保留草稿；成员只有查看权限。评审来源新增“定时同步”。

## 失败与恢复

每个仓库的读取有分页、请求和时间预算。仓库失败不阻断其他仓库；返回安全错误描述，不包含上游响应、令牌或请求 URL。失败按指数退避，最长 15 分钟；成功后恢复项目间隔。同步计划和基线在重启后继续生效，项目锁随进程退出释放。

自动任务继续使用现有重试上限、评论发布幂等和合并对账。耗尽重试的同一提交不会每轮重新调用 AI，可手动重试。合并仍要求当前提交、完整评审、阻断问题、总评同步及 GitLab 合并条件全部满足。

## 验收与部署

验证激活旧提交不入队、新 MR/新 SHA 入队、双触发去重、运行时新提交不丢失、多仓库同 IID 隔离、分页、草稿与暂停、失败退避、重启恢复、配置权限以及界面保存与错误处理。

运行前后端完整测试、迁移一致性检查、生产构建和 Docker 检查。通过 GitHub Actions 构建不可变镜像，备份服务器数据库后更新原 Compose 服务。启用混沌与应急的 60 秒同步，确认现有三个 MR 只进入基线、没有自动评审任务。通过真实只读同步验证四个仓库；不创建或合并真实测试 MR。
